# TaskSAT Grammar Reference

## Top-Level Structure

```
tasknet <identifier> {
  end = <number>;
  param <PARAM_NAME> = <value>;
  timelines { ... }
  initial { ... }
  final { ... }
  taskdef <name> { ... }
  task <name> : <taskdef> { ... }
  constraints { ... }
  properties { ... }
}
```

## Timelines

```
<name> : state(<state1>, <state2>, ...) = <initial_state>;
<name> : bool = <true|false>;                                            # Syntactic sugar for state(true, false)
<name> : atomic = <0|1>;                                                 # Mutex enforcement via [0,1] integer bounds
<name> : cumulative [<min>, <max>] bounds [<min>, <max>] = <initial>;
<name> : rate [<min_rate>, <max_rate>] bounds [<min>, <max>] = <initial> initial_rate = <rate>;
<name> : claimable [<min>, <max>] = <initial>;
```

**Timeline types:**
- **state**: Discrete values (named or numeric)
- **bool**: Boolean state (syntactic sugar for `state(true, false)`)
- **atomic**: Integer [0,1] for mutual exclusion (only cumulative impacts `+= 1`, `-= 1` allowed)
- **cumulative**: Continuous resource with range and bounds
- **rate**: Continuous resource that changes at a rate over time
- **claimable**: Resource that can be claimed and released

## Parameters

Parameters allow you to define reusable constants and avoid magic numbers.

```
# TaskNet-level (global scope)
param <PARAM_NAME> = <value>;

# TaskDef-level (defaults for instances)
taskdef <name> {
  param {
    <PARAM_NAME> = <value>;
    <PARAM_NAME> = <GLOBAL_PARAM>;  # Can reference global params
  }
  duration <PARAM_NAME>;
}

# Task-level (instance overrides)
task <name> : <taskdef> {
  param {
    <PARAM_NAME> = <value>;  # Overrides taskdef/global
  }
}
```

**Resolution order (highest to lowest priority):**
1. Task-level params
2. TaskDef-level params
3. TaskNet-level params

**Parameter references can be used in:**
- Task durations: `duration <PARAM>;`
- Task start/end times: `start <PARAM>;`
- Time ranges: `start_range [<MIN_PARAM>, <MAX_PARAM>];`
- Timeline bounds: `battery : rate [0.0, <CAPACITY>] = <INITIAL>;`
- Impact values: `battery += <CHARGE_AMOUNT>;`
- Constraint formulas: `battery >= <SAFE_LEVEL>`

## Tasks

```
taskdef <name> {
  param { <PARAM_NAME> = <value>; }
  id <number>;
  priority <number>;
  duration <number | PARAM_NAME>;
  duration_range [<min>, <max>];
  start <number | PARAM_NAME>;
  start_range [<min>, <max>];
  after <after_item>, ...;
  containedin <containedin_item>, ...;
  pre { <constraints> }
  inv { <constraints> }
  post { <constraints> }
  impacts {
    pre { <impacts> }
    maint { <impacts> }
    post { <impacts> }
  }
}

task <name> : <taskdef> {
  param { <PARAM_NAME> = <value>; }
  ...
}
optional task <name> : <taskdef> { ... }
request task <name> : <taskdef> { ... }

# Task instance ranges (compact syntax for multiple instances)
task <name>[<count>] : <taskdef> { ... }                    # All optional
task <name>[<min>..<max>] : <taskdef> { ... }               # min required + (max-min) optional
request task <name>[<min>..<max>] : <taskdef> { ... }       # min required + (max-min) request
```

**Task instance ranges** create multiple task instances with auto-generated names:
- `task science[3]` → `science_0`, `science_1`, `science_2` (all optional)
- `task science[2..4]` → `science_0`, `science_1` (required), `science_2`, `science_3` (optional)
- `request task science[1..3]` → `science_0` (required), `science_1`, `science_2` (request)

Expanded tasks inherit all properties from the range declaration.

## Task Dependencies

### After (with optional time gap)

```
# Syntax
after <after_item>, ...;

# After item variants
<task_or_taskdef>                    # No gap: B.start >= A.end
<task_or_taskdef> [<min>, <max>]    # Gap range: B.start ∈ [A.end + min, A.end + max]
<task_or_taskdef> <num>              # Shorthand: B.start ∈ [A.end, A.end + num]

# Examples
after warmup;                        # Start after warmup ends (immediate succession allowed)
after predrive [50, 100];            # Start 50-100 time units after predrive ends
after charge 500;                    # Start within 500 time units after charge ends
after A [10, 20], B 30, C;           # Multiple dependencies with different gaps
```

### Containedin (with optional start/end offsets)

```
# Syntax
containedin <containedin_item>, ...;

# Containedin item variants
<task_or_taskdef>                                              # No offsets: exact containment
<task_or_taskdef> [<s_min>, <s_max>] [<e_min>, <e_max>]      # Full ranges for offsets
<task_or_taskdef> <num1> <num2>                               # Shorthand: [0, num1] [0, num2]
<task_or_taskdef> <num>                                       # Shorthand: [0, num] [0, num]
<task_or_taskdef> <offset1> <offset2>                         # Mixed: each offset can be range or number

# Offset semantics
# Start offset [s_min, s_max]: child.start ∈ [parent.start + s_min, parent.start + s_max]
# End offset [e_min, e_max]: child.end ∈ [parent.end - e_max, parent.end - e_min]

# Examples
containedin daylight;                          # Exact containment within daylight
containedin warmup [5, 10] [5, 10];           # Start 5-10 after warmup starts, end 5-10 before warmup ends
containedin window 100 200;                    # Start within 100 of start, end within 200 of end
containedin observation 50;                    # 50 time unit margins on both sides
containedin parent 10 [20, 30];                # Mixed: shorthand start (0-10), full range end (20-30)
```

## Constraints

```
<timeline> = <value>
<timeline> in [<min>, <max>]
<timeline> < <number>
<timeline> <= <number>
<timeline> > <number>
<timeline> >= <number>
```

## Impacts

```
<timeline> = <value>       # Assignment (value impact)
<timeline> += <delta>      # Cumulative add (value impact)
<timeline> -= <delta>      # Cumulative subtract (value impact)
<timeline> +~ <delta>      # Rate add (rate impact)
<timeline> -~ <delta>      # Rate subtract (rate impact)
<timeline> =~ <value>      # Rate assignment (rate impact)
```

**Impact types:**
- **Value impacts** (`=`, `+=`, `-=`): Modify timeline value at zone boundaries
- **Rate impacts** (`+~`, `-~`, `=~`): Modify rate of change (rate timelines only)

## Temporal Logic

### Atomic Formulas
```
true
false
<timeline> = <value>
<timeline> in [<min>, <max>]
<timeline> <op> <number>
active(<task>)
```

### Logical Operators
```
not <formula>
<formula> and <formula>
<formula> or <formula>
<formula> -> <formula>
```

### Temporal Operators
```
always <formula>
eventually <formula>
<formula> until <formula>
sofar <formula>
once <formula>
<formula> since <formula>
```

### Sequential Ordering
```
sequence [<task1>, <task2>, ...]
```

Syntactic sugar for sequential task execution. Desugars to pairwise `.end <= .start` constraints.

### Mutual Exclusion
```
mutex [<task1>, <task2>, ...]
mutex [<task1>, <task2>] with [<task3>, <task4>]
```

Syntactic sugar for mutual exclusion. Desugars to non-overlap constraints: `(A.end <= B.start) or (B.end <= A.start)`.

### Constraints vs Properties
```
constraints {
  prop <name>: <formula>;      # Named constraint
  <formula>;                   # Unnamed constraint (auto-named)
  mutex [<task1>, <task2>];    # Unnamed mutex (auto-named as "mutex_task1_task2")
  sequence [<task1>, <task2>]; # Unnamed sequence (auto-named as "sequence_task1_task2")
}

properties {
  prop <name>: <formula>;      # Named property
  <formula>;                   # Unnamed property (auto-named as "constraint_N")
}
```

**Auto-naming rules:**
- `mutex [A, B]` → `"mutex_A_B"`
- `mutex [A, B] with [C, D]` → `"mutex_A_B_with_C_D"`
- `sequence [A, B]` → `"sequence_A_B"`
- Generic formulas → `"constraint_N"` (counter-based)

## Dependencies

```
after <task_id>, ...;
containedin <task_id>, ...;
```

## Initial Constraints

Hard constraints on timeline state at time 0 (restrict which schedules are valid).

```
initial {
  <timeline> = <value>;
  <timeline> in [<min>, <max>];
}
```

## Final Constraints

Checked as a property (NOT a constraint): for every valid schedule, the terminal
state — right after the last scheduled task ends (the makespan) — must satisfy
these. Same body syntax as `initial`. `final within initial { ... }` means
initial's constraints plus the ones listed; the blockless form
`final within initial;` means exactly initial's constraints.

```
final {
  <timeline> = <value>;
  <timeline> in [<min>, <max>];
}

final within initial {
  <timeline> in [<min>, <max>];
}

final within initial;
```

## Comments

TaskSAT supports both hash and C-style line comments:

```tasknet
# This is a hash-style comment
// This is a C-style comment

tasknet Example {
  end = 100;  # Inline hash comment

  timelines {
    battery : rate [0.0, 100.0] = 50.0;  // Inline C-style comment
  }
}
```

Both comment styles can be used interchangeably. C-style `//` comments are useful for block commenting in editors like VS Code (Cmd+/ or Ctrl+/).

## Example

```tasknet
tasknet RoverMission {
  end = 1000;

  # Global parameters
  param SAFE_BATTERY = 20.0;
  param DRIVE_RATE = -0.5;

  timelines {
    battery : rate [0.0, 100.0] bounds [0.0, 100.0] = 50.0 initial_rate = 0.01;
    location : state(base, site_a, site_b) = base;
    rover_active : atomic = 0;
  }

  taskdef drive {
    param {
      MIN_DURATION = 10;
      MAX_DURATION = 50;
    }

    duration_range [MIN_DURATION, MAX_DURATION];
    pre {
      battery >= 30.0;
      rover_active = 0;
    }
    inv {
      battery >= SAFE_BATTERY;
      rover_active = 1;
    }
    impacts {
      maint {
        battery +~ DRIVE_RATE;
        rover_active += 1;
      }
    }
  }

  task drive_to_a : drive {
    param {
      MAX_DURATION = 40;  # Override: shorter max duration
    }
    start_range [0, 100];
    impacts {
      post {
        location = site_a;
      }
    }
  }

  properties {
    prop battery_safety:
      always (rover_active = true -> battery >= SAFE_BATTERY);

    prop mission_completion:
      eventually (location = site_a);
  }
}
```
