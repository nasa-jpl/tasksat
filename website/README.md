# TaskSAT Documentation Site — How the Machinery Works

The documentation site is built with [Docusaurus](https://docusaurus.io/) (v3,
React 19) and deployed to **GitHub Pages** at
<https://nasa-jpl.github.io/tasksat/>. This README is the single reference for
everyone touching the docs: how to run it, how content is organized, how the
grammar pages are auto-generated from the parser, and how deployment happens.

---

## 1. Prerequisites

- **Node.js >= 20** and npm (the site build). On macOS: `brew install node`.
- **Python 3** (>= 3.9). Required because the build auto-generates the **Formal
  Grammar** page from the parser (see §4). `npm run build` / `npm run start`
  will fail if `python3` is not on `PATH`.

## 2. Commands

Everyday loop — preview your doc edits locally:

```bash
cd website
npm run start      # then open http://localhost:3000/tasksat/  (Ctrl-C to stop)
```

Edits to files under `docs/` hot-reload in the browser on save; changes to
`docusaurus.config.js` or `sidebars.js` need a restart.

All commands:

```bash
npm install        # first time only
npm run start      # local dev server with hot reload (http://localhost:3000/tasksat/)
npm run build      # production build into ./build
npm run serve      # serve the production build locally
npm run gen:grammar  # regenerate the grammar files by hand (normally automatic)
npm run gen:api      # regenerate the Sphinx API reference into static/api/ (see §5)
```

> The site is served under the **`/tasksat/`** base path (see `baseUrl` in
> `docusaurus.config.js`), so the local URL is `http://localhost:3000/tasksat/`,
> not `http://localhost:3000/`.

## 3. Directory layout

```
website/
  docs/                     # all documentation pages (Markdown, CommonMark)
    intro.md                #   landing page (slug: /), the project overview
    getting-started/        #   category "Getting Started"
      _category_.json       #     category label / order / collapsed
      installation.md
      tutorial.md
    reference/              #   category "Language Reference"
      manual.md
      grammar.md            #     readable, curated grammar
      grammar-formal.md     #     AUTO-GENERATED exact grammar (do not edit)
    theory/                 #   category "Theory"
      smt-encoding.md
      cegis.md
  src/
    pages/index.js          # the homepage (React)
    components/             # homepage feature components
    css/custom.css          # global theme overrides
  static/                   # assets served as-is (e.g. /img/architecture.png)
  docusaurus.config.js      # site config (navbar, footer, prism, markdown mode)
  sidebars.js               # sidebar (autogenerated from the docs/ folder tree)
  package.json              # scripts + the prebuild/prestart grammar hook
```

### Content model / single source of truth

- The **project overview** (features, generated files, web UI, MEXEC, etc.)
  lives only in `docs/intro.md`. The repo-root `README.md` is intentionally a
  short pointer to the site so the two never drift.
- Developer/internal notes that are **not** meant for end users live in the
  repo-root `doc/` folder (e.g. `benchmarks.md`, `performance.md`,
  `time-boundaries-feature.md`, `property-verification-enhancements.md`). They
  are deliberately kept off the site.

### Sidebar & categories

`sidebars.js` uses `{type: 'autogenerated', dirName: '.'}`, so **the folder tree
is the sidebar**. To control it:

- **Order a page**: `sidebar_position` in the page front matter.
- **Rename a page's sidebar entry**: `sidebar_label`.
- **Keep a clean URL** regardless of folder depth: `slug: /my-page`.
- **Make a folder a category**: add `_category_.json` with `label`, `position`,
  `collapsed`.
- **Gotcha**: never name a file the same as its folder (e.g.
  `getting-started/getting-started.md`) — Docusaurus would promote it to the
  category's index/link page. That is why the install page is
  `getting-started/installation.md`.

### Markdown mode (important)

`docusaurus.config.js` sets `markdown.format: 'detect'`, which means `.md` files
are parsed as **CommonMark**, not MDX. This is deliberate: docs contain
angle-bracket placeholders like `<name>` and brace snippets that MDX would try to
parse as JSX. Consequences:

- Use **HTML comments** `<!-- ... -->`, not `{/* ... */}`.
- `onBrokenLinks: 'throw'` — a bad internal link fails the build. Use relative
  `.md` links between pages.

## 4. The grammar machinery (auto-generated pages)

There are **two** grammar pages, from different sources:

| Page | File | Source | Maintained |
|------|------|--------|------------|
| **Grammar** (readable) | `docs/reference/grammar.md` | hand-written | manually |
| **Formal Grammar** (exact) | `docs/reference/grammar-formal.md` | the parser | **auto-generated** |

The exact grammar pipeline, all rooted in `src/smt/`:

```
tasknet_parser.py  (PLY grammar docstrings + `reserved` token table)
        │
        ├─ extract_grammar.py ───────────────► grammar.txt        (raw EBNF, token names)
        │
        └─ gen_grammar_doc.py ──┬────────────► grammar.txt        (also refreshes it)
                                └────────────► docs/reference/grammar-formal.md
                                               (prettified EBNF: LBRACE→"{", SEMI→";",
                                                TASKNET→"tasknet", name/number/string,
                                                ε for empty productions)
```

- `gen_grammar_doc.py` reads productions **straight from the parser** (via
  `extract_grammar`) and the `reserved` keyword table, so the page can never
  drift from the real grammar.
- It writes a page with `sidebar_position: 3`, `slug: /grammar-formal`, and an
  `ebnf` code block. `ebnf` highlighting is enabled via
  `prism.additionalLanguages` in `docusaurus.config.js`.

### It runs automatically

`package.json` wires it into the lifecycle:

```json
"gen:grammar": "python3 ../src/smt/gen_grammar_doc.py",
"prestart":    "npm run gen:grammar",
"prebuild":    "npm run gen:grammar"
```

npm runs `prestart` before `start` and `prebuild` before `build`, so both local
dev and CI regenerate the grammar page before serving/building. You normally
never run `gen:grammar` by hand — but you can after a parser change to preview.

The generated files (`grammar-formal.md`, `grammar.txt`) are committed for
convenience, but the build overwrites them, so the deployed site always matches
the current parser.

## 5. The API reference (Sphinx)

The **code** documentation — everything under `src/smt/` — is a separate
[Sphinx](https://www.sphinx-doc.org/) `autodoc` site generated from the module
docstrings, published *inside* this site at
<https://nasa-jpl.github.io/tasksat/api/>.

```
doc/api/                    # Sphinx sources (committed)
  conf.py                   #   autodoc/napoleon/furo config
  index.rst                 #   landing page + toctree
  pipeline.rst              #   ast, parser, transforms, wellformedness, smt,
                            #     realizability, compositional, verifier, printer
  visualization.rst         #   gantt, timeline/temporal/structure viz, color_utils
  tooling.rst               #   web UI, grammar tooling
        │
        └─ npm run gen:api ──► website/static/api/   (generated HTML, gitignored)
                                       │
                                       └─ copied verbatim into the Docusaurus
                                          build → /tasksat/api/
```

Because Docusaurus copies `static/` into its output untouched, the API docs ship
in the **same** Pages deployment as the rest of the site — one build, one URL, no
second workflow. The navbar "API" link uses `to: 'pathname:///tasksat/api/'`; the
`pathname://` prefix is required so Docusaurus emits a plain link instead of a
client-side route (and skips broken-link checking on it).

- **Run it**: `npm run gen:api`. Needs `pip install -r requirements.txt -r
  requirements-docs.txt` — the runtime deps too, since autodoc *imports* every
  module it documents.
- **It is not in `prestart`**, only `prebuild` — it would add ~15s to every
  dev-server boot. Run it by hand once and `npm run start` serves
  `http://localhost:3000/tasksat/api/` from `static/` like any other asset.
- **PLY plumbing is hidden**: an `autodoc-skip-member` hook in `conf.py` drops
  the 221 `p_*` / `t_*` functions of `tasknet_parser`, whose docstrings are BNF
  productions rather than prose (that grammar is §4's job).
- **Docstrings are reStructuredText.** Keep them RST-clean: a blank line before
  a bullet/numbered list, `::` before an indented code/literal block, and
  backticks around anything with `*` or `|` in it. `default_role = 'literal'`
  means single backticks render as code, so Markdown-style `` `foo` `` is fine.
  The build must stay at **0 warnings**.

## 6. Deployment

GitHub Actions workflow: `.github/workflows/deploy-docs.yml`.

- **Triggers** on push to `main` when `website/**`, `src/smt/**`, `doc/api/**`,
  or the requirements files change — so editing a docstring or the parser alone
  still redeploys. Also runnable manually via *workflow_dispatch*.
- **Build job**: checkout → setup-node 20 → setup-python 3.11 → `npm ci` →
  `pip install -r requirements.txt -r requirements-docs.txt` → `npm run build`
  (the `prebuild` hook regenerates the grammar page *and* the API reference) →
  upload `website/build` as a Pages artifact.
- **Deploy job**: publishes the artifact to GitHub Pages
  (`actions/deploy-pages`). Pages source must be set to **GitHub Actions** in the
  repo settings.

No `gh-pages` branch is used; deployment is artifact-based.

## 7. Common tasks

- **Add a page**: drop a `.md` in the right `docs/<category>/` folder with front
  matter (`sidebar_position`, optional `sidebar_label`, optional `slug`).
- **Add a category**: create a folder + `_category_.json`.
- **Add an asset**: put it in `static/` and reference it as `/img/...`.
- **Change the parser grammar**: just edit `tasknet_parser.py` — the Formal
  Grammar page updates itself on the next build. Run
  `python3 src/smt/gen_grammar_doc.py` if you want to see it immediately.
- **Document code**: write a docstring in `src/smt/` — it appears on the API
  site on the next build. Preview with `npm run gen:api`.
- **Add a module to the API site**: add an `.. automodule::` entry to the right
  `doc/api/*.rst` page (nothing is auto-discovered, on purpose).
